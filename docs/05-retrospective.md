# 05 工程复盘与下一步

本复盘由 AI 根据本轮实现与实际测试起草，记录工程观察；不冒充候选人的个人经历或学习心得。候选人应复现后补充自己的理解与取舍。

## 最难的问题

确认边界比工具串行调用更容易出错。18:00 被占用时，“建议 19:00”“用户确认 19:00”“草稿已保存”“已发布”是不同事实。将原要求、建议时段、确认状态和保存返回分别存储，并由工具强制执行，可以避免模型一句话改变权限或造成虚假成功。

幂等和无冲突也需要同时成立。只用内存记录去重，两个进程仍可能抢到同一时段；只用时段唯一约束，又难以识别同一请求的再次提交。因此选择请求唯一键、请求指纹、时段唯一键与 SQLite 事务共同保证。并发测试证实同一时段至多一个写入成功。

## 本轮获得的工程认识

真实模型首轮只通过 11/13：补查后直接结束导致缺少新审核，临时查询失败后也没有恢复。执行器如实返回 incomplete/failed，未出现越权保存。随后把“每次读取使旧审核失效”和“暂时只读错误可补查一次”写入明确的工具契约与提示，再跑同一完整矩阵达到 13/13。两轮原始记录都保留，详见 [live-evidence.md](live-evidence.md)。

- 草稿是否存在必须由存储和工具返回证明，不能相信模型总结。提前 finish、保存失败和预算耗尽都需要单独处理。
- 信息不足应先说明缺口；缺少渠道元数据与已知渠道不授权是两类不同事实。本轮据此修正了审核逻辑。
- Mock 能快速检查异常边界，但固定策略通过再多场景，也不能证明模型会根据新结果作出合理决策。
- 可重复执行的输入、排期快照、故障配置、实际输出与 Trace，比截图更便于评审核对差异。

## 当前取舍

为保证离线环境可运行，使用标准库和 SQLite，省去界面、框架依赖与部署。代价是仅支持离散小时窗口、快照排期与本地可信用户输入。没有为追求目录规模而加入多 Agent 或生产级调度设施。

## 下一步优先级

1. 扩大真实模型评估的资料变化与重复次数，衡量稳定性；重点改进确认状态在简短理由中的偶发措辞错误，仍以工具状态作为事实。
2. 候选人复核核心约束并完善个人理解；如有实际修改或手工复跑，再按事实补充原因、结果与用时。
3. 若扩展业务，优先增加已认证用户确认、草稿取消和占位过期，再考虑实时外部排期同步。
4. 只有确有需要时再增加界面和部署；仍只保存草稿，真实发布需要单独设计与授权。

## 交付边界

真实模型评估、离线测试、AI 使用与贡献记录均已完成并归档。候选人手工复跑没有已确认记录，个人投入时间未单独计时，贡献文档据实披露。项目为公开 GitHub 仓库，交付 SHA 以最终远程核验为准。真实视频语义审核、多人身份认证、实时外部排期同步和统计稳定性评估仍在范围之外。
